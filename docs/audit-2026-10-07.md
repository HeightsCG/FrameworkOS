# Codebase audit, 2026-10-07

Scope: the whole `framework/` checkout at `main` (clean tree), 365 PHP files, plus `public/js` and the email layer. Method: seven parallel read-only reviews by area (auth and sessions; money; admin, team and support; posts, media and profile; messaging, events and live; MCP, AI pipeline and integrations; cross-cutting XSS), then an independent verification pass on every candidate. Only findings confirmed at confidence 8/10 or higher are listed as findings. Nothing was changed in the code.

Overall: the codebase is in good shape for its size. Parameter binding is universal, every `/api` call is POST plus CSRF, ownership checks are consistent in the model layer, credit debits are row-locked, paid media is signed only after entitlement, SSRF and shell arguments are handled properly, and views escape by default. The problems below are concentrated in a few seams between subsystems: Google sign-in and local accounts, custom domains and the platform session, team roles and live calls, and the two write paths (web UI vs MCP) that store different representations of the same field.

## Findings

### 1. High: Google sign-in links to an unverified password account (pre-account takeover)

- Where: `app/controllers/AccountController.php:360-363` and `app/models/UsersModel.php:400-403` (`link_google`).
- What: when no row matches the Google `sub`, the callback looks the account up by email and, if that row has no `google_sub`, calls `link_google`, which sets `google_sub` and `email_verified = 1`. It never checks that the local row was verified by our own flow, keeps the local password, and sends no notice.
- Exploit: attacker registers with the victim's email and a chosen password (the row stays unverified and unusable). Victim later clicks "Continue with Google": the row is linked, marked verified, and the victim is signed in silently. Attacker now logs in with email plus their password; the verify gate passes. Full takeover unless the victim later enabled MFA. Attacker can also change the email because they know the "current password".
- Fix: only auto-link when `email_verified === 1`; otherwise refuse and ask the user to sign in with their password and connect Google in Settings. If auto-link must stay, rotate the password hash to random, clear MFA and pending tokens, and email the address. Secondary: re-verify on email change in `update_profile`; stop returning `invite_link` in the `team_invite` JSON.

### 2. High: custom-domain handoff gives a creator-controlled host the visitor's full platform session

- Where: `app/Bootstrap.php:79-98` (`redeem_handoff`), `app/controllers/AccountController.php:401-411` (`domain_loginAction`), `libs/Classes/CustomDomains.php:23` (`PASSTHROUGH` includes `api`), `app/models/CreatorDomainsModel.php:19-26` (`status IN ('verified','active')`).
- What: `/_handoff` starts the user's complete session on the creator's domain (same server-side session store, no host binding) and `/api/*` works there, so that cookie can call every API action. `domain_login` is a bare GET that, for any signed-in user, immediately mints a handoff to any live host with no confirmation and no admin exclusion. Hosts in `verified` state (TXT only, DNS not at the gateway) count as live.
- Exploit: a Studio creator lures signed-in users (fans, other creators, admins) to `/account/domain_login?host=<their domain>`. They control the DNS zone, so they can route the host (or its `verified` www twin) to their own server to harvest the session cookie or the raw handoff token, then route back to the gateway and replay the cookie: read inbox, send DMs, spend credits with the card on file, mint an MCP token, delete the account, and run every `admin_*` action if the victim is staff.
- Fix: never hand off admins; make `domain_login` for a signed-in user a POST-plus-CSRF interstitial ("Continue to example.com as @you?"); require `status = 'active'` in `get_live_by_hostname`; and scope custom-domain sessions narrowly, for example an allowlist of read-only creator-scoped API actions instead of passing all of `api` through.

### 3. Medium: late registration unlocks a paid event replay for free

- Where: `app/controllers/api/ApiEventsController.php:89-140` (`event_registerAction`), `libs/Classes/EventReplay.php:28-36`.
- What: registration has no start/end time check (only the profile hides the button client-side), and replay access grants `attendee` to any `registered` row when "free for attendees" is on, which is the default.
- Exploit: after a free event ends and the replay goes on sale, a fan registers, then calls `event_replay_watch` and receives the four-hour signed MP4 URL. For paid events, a late ticket cheaper than the replay does the same, and the ticket is paid out to the creator by the earnings cron.
- Fix: refuse registration once the event has ended (same rule as `is_past` in `ProfileController`); in `EventReplay::access` honour only registrations created before the end; do not reactivate canceled rows after the end.

### 4. Medium: view-only team members get full host powers on live calls

- Where: `libs/Classes/LiveAccess.php:37` (`is_host`).
- What: `is_host` checks `creator_id()` and `can_act_as_creator()` but never `team_allows()`, so a Viewer collaborator passes. Every host endpoint, the LiveKit token with `roomAdmin`, the call password on the page, recording control, the buyer check on 1:1 booking calls, and free replay access all rely on it. The event and service workspaces themselves require `manage`.
- Fix: add `&& Permissions::team_allows('manage')` (or `'content'` if Editors should host).

### 5. Medium: admin impersonation can spend the user's wallet

- Where: `libs/Classes/UserSession.php:17-28` (`IMPERSONATION_BLOCKED`); sinks `app/controllers/api/ApiEventsController.php:255` and `app/controllers/api/ApiLiveController.php:261`.
- What: the blocklist covers three of the five `CreditsModel::pay()` call sites but not `event_replay_buy` and `live_tip`. `CreditsModel::pay()` itself has no impersonation check, and nothing done while impersonating is written to the admin audit log (the `AuditTrail` trait is only mixed into admin controllers).
- Exploit: a staff account with its own creator event replay on sale impersonates a fan, buys the replay, and the fan's wallet pays the staff member's creator account.
- Fix: add both actions to the list, and refuse inside `CreditsModel::pay()` when `UserSession::impersonating()` so new sinks cannot be forgotten. Consider logging impersonated API calls under the impersonator id. Non-monetary omissions worth adding too: `join_free_plan`, `unblock_user`, `message_send`, `broadcast_send`, `connect_account`, `fanvue_*`, `domain_*`.

### 6. Medium: user names rendered as HTML in SweetAlert titles and toastr (XSS against creators and hosts)

- Where: `public/js/live.js:15` (quote-unsafe escaper), `:717` (attribute sink), `:684-689`; `public/js/event-page.js:114` and `:165-169`; `public/js/service-page.js:129-130`; `public/js/influencers.js:140-142`, `:610-611`, `:823`; server messages that concatenate an influencer name (`libs/Classes/InfluencerActions.php:32,34,53,105,457,459` and siblings in `InfluencerImageActions`, `InfluencerVideoActions`, `InfluencerJobService`).
- What: SweetAlert2 renders `title` as HTML (`titleText` is the safe option) and toastr 2.1.4 defaults to `escapeHtml: false`; none of the five `toastr.options` assignments change that. Three chains reach those sinks with raw names. (a) Attendee and buyer management pages escape the fan's name into `data-name`, then read it back with `getAttribute` (entity-decoded) into `confirm_action({ title: 'Refund ' + name + '?' })`. The name is entity-decoded server-side at `ApiEventsController.php:297` and comes from the fan's display name or signup first and last name, which have no validation. (b) The live-call People panel uses an `esc()` that encodes only `& < >` (not quotes), so a guest name like `x" onclick="..."` (40-char limit) injects an attribute, and the Remove handler feeds the name into a SweetAlert title and a toastr. (c) Influencer names are stored raw (`ApiInfluencersController::text()` decodes) and are concatenated into toastr messages client- and server-side.
- Exploit: a fan sets a display name containing an `<img onerror>` payload and registers for an event or books a service; when the creator clicks Refund or Remove on the management page, the script runs in the creator's session with the page CSRF token. A guest can do the same to a live-call host with no account. A team Editor can do it to the owner through an influencer name.
- Fix: one global `toastr.options.escapeHtml = true` in the shared header; use `titleText` instead of `title` in every `Swal.fire` that carries a name (`confirm_action` in event-page.js and service-page.js, live.js:685); make the live.js escaper quote-safe like `site.js:51`; strip `"'<>` from guest names server-side.

### 7. Medium: HTML injection into attendees' branded emails through the MCP event link

- Where: `app/models/NotificationsModel.php:197` (`brand_wrap` button `href`), fed by `libs/Classes/EventMail.php:40` and `app/models/EventsModel.php:140-143` (`web_link`).
- What: the button label and every other slot are escaped, but the button URL is concatenated raw. The web UI stores `external_url` HTML-encoded (safe by accident). The MCP `create_event` / `update_event` path stores the JSON string raw, and `web_link` only checks the `https?://` prefix and length.
- Exploit: a creator (or anyone holding their MCP token) sets a meeting link containing `">` followed by a fake "payment failed, update your card" block. Every registration confirmation and reminder to fans carries it inside the platform-branded Postmark email. No script runs, but it is first-party phishing.
- Fix: `htmlspecialchars($button_url, ENT_QUOTES, 'UTF-8')` at the single sink; have `web_link()` reject anything failing `FILTER_VALIDATE_URL` or containing `" < >` or whitespace.

### 8. Low: engagement endpoints skip the visibility gates that `post_detail` enforces

- Where: `app/controllers/api/ApiPostsController.php:642` (`post_engagement_ok`); sinks at `:170`, `:184`, `:205`, `:239`.

Comment lists (names, handles, bodies) for hidden, socials-only, moderation-blocked or suspended-creator posts can be read by guessing ids, anonymously for free posts.

### 9. Low: sold PPV post content can be removed from buyers

- Where: `app/controllers/api/ApiCreatorStudioController.php:768` (check only when submitted audience is `ppv`, after `update_fields` already wrote the new audience), `:884-890` (`post_delete` hard-deletes with no buyer guard), `app/controllers/api/ApiMediaController.php:444-446` and `:478-479` (library delete detaches from every post).

## Verified and rejected

- Billing double-charge race in `BillingService::charge()`: real code facts (random idempotency keys, no per-user lock), but same-session requests are serialized by PHP's file-session lock and rejected by applied state, the button is disabled client-side, and the CSRF retry fires before any charge. Only the owner racing themselves from two devices can hit it. Optional hardening: `GET_LOCK('billing:'.$uid)` in `charge()` and deterministic keys.
- Bundles selling unscanned media to adult-opted-in fans: deliberate and commented policy, applied the same way to replays and paid DMs. Posts are stricter (pending hidden from everyone). Note only.

## Lower-confidence notes (not verified to the bar above)

- Service re-booking: if the credit debit fails after the balance pre-check, `remove_purchase` deletes the reused `refunded` row instead of restoring it (events do this right via `release_registration`). Bookkeeping only. `ApiServicesController.php:160-162`.
- Chunked video upload is never content-sniffed before ffprobe/ffmpeg run on it (`ApiMediaController.php:150-200`, `:283-289`); an HLS playlist uploaded as "video" could make ffmpeg fetch arbitrary URLs. Cheap fix: run `MediaIngestService::verify_video_file()` on the first chunk.
- `IMPERSONATION_BLOCKED` is a blocklist; `AuditTrail` never records actions taken while impersonating.
- MCP bearer token is also accepted as a URL path segment (`/mcp/<token>`), so it lands in access logs. Drop the fallback or exclude the path from logging.
- Admin user page links `website_url` without a scheme check (`app/views/admin/user.php:105`); `target="_blank" rel="noopener"` mostly neutralises `javascript:` but validate `https?://` anyway.
- No Content-Security-Policy, `X-Content-Type-Options` or `Referrer-Policy` headers; `X-Frame-Options` comes only from `.htaccess`. Emit them from Bootstrap so the custom-domain gateway inherits them.
- Backslash path segment in the custom-domain `/@handle` redirect (`app/Bootstrap.php:64-66`) is rebuilt without `safe_path()`; browsers treat `/\evil.com` as `//evil.com`.
- `mfa_totp_beginAction` returns `'message' => 'Something went wrong'` on success. Passwords are `htmlentities`-encoded before hashing (consistent today, but any non-web login path would not match).
- `app/email_templates/*.html` and `Notifications::get_email_template()` substitute without escaping and have no callers (legacy branding); delete or escape before re-use.
- `carousel_start` leaves already-queued slots running and charged if `create_job` throws mid-loop, unlike `talking_start`.
- Creator-to-creator threads put the initiator on the fan side (`MessagesModel::open_between`), so they cannot attach media or price.

## Fix plans for the open items (written 2026-10-07, not yet built)

### Finding 1: Google sign-in linking to an unverified account (superseded: built as "never link by email; connect from Settings", see Status)

Goal: a row that was never verified by our own flow is never silently adopted by a Google sign-in while keeping a password someone else chose.

1. `AccountController::google_callbackAction`, the `get_one_by_email` branch. Split on `email_verified`:
   - Verified row, no `google_sub`: link as today (the owner proved the address).
   - Unverified row: take the row over for the Google user instead of just linking. One new model method, `UsersModel::adopt_for_google($user_id, $sub, $first, $last)`, in a single UPDATE: `google_sub = :sub`, `email_verified = 1`, `p_word = password_hash(random 18 bytes)` (the old password stops working), `mfa_totp_secret = NULL`, `mfa_totp_enabled = 0`, `mfa_email_enabled = 0`, `reset_token = NULL`, `reset_token_expires = NULL`, `email_verify_token = NULL`, `first_name/last_name` from Google when the row's are empty. Then `MfaModel::clear_backup_codes`. The `pw_fp` session fingerprint already ends every other session of that row.
   - After adoption, send one security email to the address ("Google was connected to your account; the previous password no longer works. If this wasn't you, reset your password.") through the existing `security` notification category with `force_email`.
2. `UsersModel::link_google` keeps its current body but is only called for verified rows; the comment is updated so nobody reuses it for the unverified case.
3. `ApiProfileController::update_profileAction`, email change branch: after the current-password check, set `email_verified = 0`, call `set_email_verify_token` and send the verification mail to the new address. The session stays signed in; the hard gate applies at the next password login, and the Google path refuses because the Google email no longer matches. Add `verify_pending` to the JSON so the settings page can show the "check your inbox" state it already has for signup.
4. `ApiTeamController::team_inviteAction`: stop returning `invite_link` in the JSON; the invitee gets it by email only. `public/js/team.js:57` drops the read-only link field.
5. Tests: register `x@example.com` with password A, sign in via Google as `x@example.com` (use the dev Google client), then `/api/login` with password A must fail with the normal wrong-password message; the security email must arrive; a verified row without `google_sub` still links as before.

No schema change. Rows already in the attacker-created state in prod would be cleaned up by the adoption on the victim's next Google sign-in.

### Finding 2: custom-domain session handoff

Goal: a creator's domain never receives more authority than a fan needs there, and nobody is handed off without asking.

1. **Never hand off staff.** In `AccountController::domain_loginAction`, `Bootstrap::custom_domain_route` and `Bootstrap::return_to_custom_domain`: when `Permissions::is_admin()` is true, send the admin to the platform page instead of minting a handoff. Admins browse creator domains signed out.
2. **Confirm before leaving.** `domain_loginAction` for a signed-in user no longer redirects on GET. It renders a small interstitial on the platform host ("Continue to lexivaughn.com as @you?" with Continue and Cancel). Continue is a POST with the CSRF token that mints the handoff. Signed-out users keep the current flow (sign in, then return). The links on creator pages that point at `/account/domain_login` do not change.
3. **Only live DNS counts.** `CreatorDomainsModel::get_live_by_hostname` requires `status = 'active'`. A `verified` domain (TXT only) is not served and not a handoff target until `cron/domains.php` sees it at the gateway; the domains card in Settings already shows the "waiting for DNS" state. `cron/domains.php` demotes on the first miss instead of the second, so a domain pointed away stops being a target within a day.
4. **A fan-scoped session on the domain.** `redeem_handoff` stops calling `UserSession::start($user)`. It starts a session that holds only `user_id`, `u_name`, `domain_scope = <hostname>` and a fresh CSRF token; no `role_id`, `team_role`, `created_by`, `is_admin`. Then:
   - `Permissions::is_admin()` returns false when `domain_scope` is set; `Permissions::creator_id()` returns the user id (no team acting-as).
   - `Bootstrap`, in the `/api` branch, when `CustomDomains::current()` is set: the action must be in a new `CustomDomains::FAN_ACTIONS` allowlist or the request gets the 404 page. The list is what a fan does on a creator page: `post_detail`, `post_like`, `post_comments`, `post_comment_add`, `post_view`, `follow_creator`, `unfollow_creator`, `ppv_unlock`, `bundle_unlock`, `subscribe_plan`, `join_free_plan`, `cancel_creator_subscription`, `message_send`, `message_unlock`, `event_register`, `event_cancel`, `event_replay_buy`, `event_replay_watch`, `service_purchase`, `service_access`, `live_join`, `live_tip`, `live_status`, `report_user`, `block_user`, `promo_preview`, `notifications_*` read-only ones. Everything about billing, cards, wallet top-ups, account, MFA, MCP tokens, team, data export, admin, studio and influencers is refused.
   - Every allowlisted action that takes a creator or object id already looks the object up; add one check in `BaseApiController` for domain-scoped sessions: the resolved creator id of the object must equal the domain owner's id (`CustomDomains::current()['user_id']`), otherwise "Not available on this site". This stops a stolen cookie being used against a different creator.
   - Pages on the domain are already limited to the profile, events, services and live routes; nothing else changes.
5. **Short-lived.** Domain sessions expire after 7 days of inactivity (store `domain_scope_at`, checked in `Bootstrap` on custom hosts); the platform session is untouched and the fan re-confirms through step 2 when it lapses.
6. Residual risk after this: a creator who re-points DNS to their own server can still capture a fan's domain session and spend that fan's existing wallet credits on that creator's own content, or read their DM thread with that creator. That is bounded to one creator and one wallet, and the creator is a paying, verified account you can suspend and claw back from. If that is not acceptable either, the alternative is checkout-on-platform: unlock/subscribe buttons on the domain redirect to the platform host for the purchase and come back, and the domain session becomes read-only. That is the bigger product change and I'd only do it if you want it.
7. Tests: admin clicks a domain link and lands on the platform page, not the domain; a fan gets the interstitial and only moves after Continue; a `verified` domain 404s at the gateway and is refused by `domain_login`; on the domain, `/api/buy_credits` and `/api/admin_*` return 404 while `ppv_unlock` for that creator works and `ppv_unlock` for another creator's post is refused; `Permissions::is_admin()` is false for an admin's leftover domain session.

No schema change. Existing domain sessions keep working until they next hit the handoff; the stricter checks apply at once.

### Finding 15: Free creators and AI-credit purchases
